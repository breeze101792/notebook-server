List editor — the Edit list window

One list container, as a flat document-order treegrid in the shared edit-window chrome. Every number is the spec's: header 65, bar 57, footer 69, row 27, indent 18, selection and done cells 18, selection box 14, done ring 16, marker slot 20, targets 32 / 44. Boards are drawn at the shipped width for their viewport (§9.1); the app's height is min(85vh, 92vh), drawn here at a fixed height so a board fits a page. The chrome is drawn for context; the body is the part this document owns. Toggle the theme to check both palettes.

Eleven boards. No network assets, no web font. Markup is complete with scripting off; the only script is the theme switch. Board 1 carries the contracted ids.

1 · Open — 14 items, nothing selected, 2 done

The badge reports the container type only. Nothing is selected: the first row has focus and the anchor, and the status is the opening counts with no result phrase. Focus on a first row also means Up, To top, Outdent, Indent, Select none and Mark open are disabled — each carries its cause (§4.3). This board is the contracted DOM: the overlay, every footer and header id, #le-toolbar, the fourteen le-* controls and the hidden notice strip.

100 rows is the comfortable budget; 1000 is not supported and there is no hard cap — a longer list still opens and this window simply stops promising speed. Nothing is virtualised: all 120 rows are in the DOM, one repaint per verb, and the marker column was measured once from the widest visible marker.

The mockup is illustrative; list-editor.md is normative. Boards draw only states the spec names: no applying board (Apply is synchronous), no drag board (v1 has no drag inside the window), no blocked board (an unopenable target opens nothing). Every toolbar is static markup, so the boards render with scripting off; the only script is the theme switch.
