Top bar — the session picker

The active session's name in the top bar becomes a picker with the workspace chip's face: Notebook │ Notes │ Deep work ▾. Clicking the name you are reading opens the sessions that name could be, in place, without a trip to the rail. This file illustrates docs/ui/topbar-session.md as it is being revised to the picker; where the two differ, the spec wins.

Read this with the spec. This mockup is the visual argument; topbar-session.md is the normative source for markup, CSS, JS, states, ARIA and acceptance criteria. It currently documents the static label, and will be revised to the picker drawn here.

1 · In the shell — picker open, Sessions panel open

One element changed: the label became a button with the chip's chrome, and the popover hangs from it. The Sessions view stays open beside it, because the picker is a second door to the same list, not a replacement. The two active rows name the same session — the popover's Deep work and the panel's Deep work are one fact read twice, not two states that could disagree.

Why the trigger is a control now. The bar already says which session you are in; the moment that name is the thing you want to change, the shortest path is the name itself. The rail still opens the full view — with rename and delete in it — but that is one click away from a bar you are already looking at. A name you read is a name you will reach for.

Why the popover is attached to the trigger, not the pointer. This is a menu of siblings: the same place every time, left edge under the name that opened it, check column under the glyph. A pointer-positioned menu lands wherever the last click was, which makes the same list look like a different list each time. The caret is the promise that the list belongs to that button.

The open menu covers the tab strip, not the panel. The app paints the popover above the editor, so the Sessions rows stay visible and the two names can be compared in one frame: both say Deep work. The picker does not replace the panel — it is the same fact, reached from the bar instead of the rail.

2 · Trigger states

Four faces, one 28 px box. Resting is the workspace chip's face; hover and expanded are the chip's hover and expanded faces; focus is the same 2 px accent ring at the same 1 px offset. A still frame has no pointer, so .is-hover and .is-focus force the two faces — the app uses :hover and :focus-visible.

resting — beside the chip it now matches

hover — --accent-soft face, --accent border

focus-visible — 2 px ring, 1 px offset

expanded — same face as hover, caret rotated 180°

expanded + focus — the caret and the ring are two signals, not one

a 40-character name — ellipsised, with its tooltip drawn

Why the two pickers look identical. Both answer “which one am I in?” and both open a list. Giving the session trigger a lighter face would say “this one is only informational”, which is exactly what it is not; giving it a heavier face would make the workspace chip look like the secondary control, and the workspace is the outer container. Same chrome, same 28 px height, same caret behaviour. The tooltip above is drawn, not a live title: the name caps at 40 characters and the trigger caps at 240 px, so a long name always ellipsises and the full string is always one hover away.

3 · The popover, measured

Same object as the workspace picker: 300 px wide, 8 px radius, 4 px padding, 32 px rows, 6 px gap under the trigger, 420 px ceiling. The numbers are not a new vocabulary — they are copied so the two menus in one bar cannot drift apart.

6 px
32 px row 8 px radius 4 px padding 300 px
  • 300 pxWidth. Fixed, not shrink-to-fit: a name that ellipsises inside a fixed column keeps the check, dot and count in one place. The row names yield; the chrome does not.
  • 6 pxGap. The caret points down at the popover; 6 px is close enough to read as attached and far enough that the trigger's hover face is not touched.
  • 4 pxPadding. The first row's hover face stops 4 px inside the frame, so the popover reads as a container rather than a stack of rows.
  • 32 pxRow. A 32 px target in a 300 px menu, the same as the workspace picker. Eight of them fit without a scroll.
  • 14 pxCheck column. Empty on inactive rows, so the names never shift as the active session changes. The same column the workspace picker uses.
  • 8 pxDirty dot. The same 8 px accent dot as the panel row and the dirty tab, so the three never disagree about which session has unsaved edits.
  • 420 pxCeiling. max-height: min(70vh, 420px). Twenty sessions scroll instead of growing the menu over the editor.
  • 8 pxRadius. The workspace popover's radius. Two menus of the same kind in one bar share one corner.

row states — rest · hover · focus (roving tabindex) · active

Positioning, and what this still frame cannot show. In the app #session-menu is moved to <body> and positioned fixed: 6 px below the trigger's left edge, flipped above the trigger when it would overflow the viewport, and clamped 8 px from the left and right edges. Here it is position: absolute inside a positioned wrapper, so one static page can show it attached to the button that owns it.

Why the active row has no tinted face. The check, the accent text and the 600 weight are three cues already; a fourth would paint the one row that cannot be hovered, which makes it look pressed. Hover on the active row stays transparent — the row is where you already are, so hovering it must change nothing.

4 · Who sees the New row

The picker switches sessions; it does not create them for everyone. Admin: a separator and a New session… row, so creating one is reachable from the bar. Viewer: no separator, no row — the role cannot create a session, and a disabled row in a 32 px menu is a promise the role cannot keep. At the 20-session cap: no row either, because there is nothing to offer.

admin — 3 sessions, New available

viewer — same list, no New row

at 20 of 20 — the tail, no separator, no New row

20 of 20 — nothing follows

Why the New row is admin-only, and why it lives here at all. Creating a session belongs to the picker because the picker is where you decide which session you are in — and “a new one” is one of the answers. Renaming and deleting do not belong here: they are edits to a row that already exists, they are destructive, and the panel's ⋯ already owns them with room for a confirmation. The role check is the same one the panel's + uses, so the two surfaces can never disagree about whether creation is offered.

5 · Twenty sessions — the list scrolls, the bar does not move

Twenty rows at 32 px are 640 px of list; the ceiling is 420. The menu scrolls inside itself, the top bar keeps its 46 px, and the editor behind it is never resized. When the menu opens the app scrolls the active row into view before the first paint, so the current session is never the one you have to hunt for.

Drawn, not live: the scroll offset and the thin scrollbar thumb in the frame are page furniture. The app uses a real scroll container, so a mouse wheel, a trackpad, the keyboard and the platform scrollbar all work.

6 · Narrow desktop — 861 px

The narrowest width that is still the desktop shell, with a long brand, a long workspace name, a long session name and the popover open. The three left-hand names share the shortfall and ellipsise; the actions keep their width. The popover stays inside the viewport because it is aligned to the trigger's left edge, not centred on it.

Why the trigger caps at 240 px, the chip's own cap. Two pickers side by side should yield at the same rate: if the session trigger could grow, it would squeeze the workspace name first at exactly the widths where both are long. The brand keeps its shipped hard clip (text-overflow does not apply to its inline-flex box) — a pre-existing quirk this feature does not change. Below 861 px the phone shell takes over and the trigger goes with the bar's desktop furniture (board 7).

7 · Top bar hidden, and the phone

With “Hide top bar” on, the picker goes with the bar — it is part of that bar. Nothing becomes unreachable, because the session list has a second door on the rail (🗂), which opens the same list with rename and delete beside it. That second door is why the picker may be top-bar-only: the workspace switch needed a rail mount because it had no other way in; the session model has one. The phone has no sessions at all, so it has no trigger.

Why hiding the bar does not cost the feature. The picker is a shortcut, not the only route: it offers switching (and, for an admin, creation) from where you are already looking. The panel offers the same switch plus rename and delete. A control that disappears with its container is fine when its job is also done one rail click away — that was not true of the workspace switch, which is why that one got a rail mount and this one does not.

8 · Light theme

The tokens swap and the geometry does not: same 28 px trigger, same 300 px popover, same faces. The active row's --accent is #2f5fd0, which is darker than the dark theme's and reads as text rather than as a highlight.
PairDarkLightVerdict
name — --fg on --bg-elev11.613.5passes 4.5:1
caret — --fg-muted on --bg-elev4.35.1a decorative glyph, aria-hidden; above 3:1 either way
active row — --accent on --bg-elev5.44.9passes 4.5:1
count — --ws-fg-muted on --bg-elev5.05.1passes 4.5:1; the panel's count token, not --fg-muted

Why the caret may sit under 4.5:1. It is a shape, not text: it is aria-hidden, its meaning is carried by the button's aria-haspopup, and 3:1 is the bar for a non-text indicator. It is --fg-muted because it must not compete with the name, and it takes --fg on hover and when expanded, like the chip's.

9 · Rejected alternatives

Three shapes that were drawn and dropped. Each one either duplicates a surface that already exists or asks one element to do two jobs — that is the reason, not taste.

DirectionVerdict
A · a session chip on the activity railRejected. It is a third mount of the same list: the 🗂 icon already opens the Sessions panel, and the workspace chip already has a rail mount for the bar-hidden case. A session glyph beside 🗂 offers two doors 40 px apart that show the same rows, and the top bar would still need the name — so the rail copy adds a control without removing one.
B · rename and delete inside the popoverRejected. The panel's ⋯ owns rename and delete, with room for a dialog, a confirmation and the “at the cap” state. Putting them on a 300 px switch surface makes the primary action of a row ambiguous (click the name to switch, or to edit?) and puts a destructive control one pixel from the thing you use forty times a day. Switching is a read; this would mix a write into it.
C · NB.menu at the cursorRejected. NB.menu is flat text: no check column, no tab counts, no dirty dot, no attached caret, and no aria-current row to inherit a roving tabindex from. It also opens at the pointer, so the list moves between clicks and detaches from the name that opened it — the opposite of what a picker attached to a named trigger needs.
